# AI 写作引擎从 0 到 1：原理与工程实践

> 面向要落地一套企业级 AI 写作引擎的开发者的技术笔记。记录从架构选型到三类写作能力实现的关键决策，可作为团队内部培训素材。

## 一、定位与目标

企业内容生产（产品文案、技术文档、营销稿、周报）存在三个痛点：产出慢、风格不一、依赖个人。AI 写作引擎的目标是把这三件事标准化：**用一个统一底座，支撑三种典型写作任务**，让非技术成员也能稳定产出高质量稿件。

三种典型任务分别是：一句话写作（多轮对话逐步成稿）、基于已有素材和报告仿写（RAG 检索参考）、基于固定模板写作（结构化填变量）。

## 二、整体架构：一块底座，三根支柱

引擎按单向依赖分层，避免循环引用，从上到下是：

- **写作编排层**：接收三类任务，按路由分派到对应生成流程；
- **Agent 核心层**：负责对话管理、记忆分层、检索工具调用与流式返回；
- **素材 RAG 层**：文档解析、切片、向量化、检索；
- **模板引擎层**：模板结构、变量配置与占位符替换；
- **存储层**：业务库（MySQL）、状态与缓存（Redis）、向量检索与模板库（Elasticsearch）。

核心原则：**业务与中间件解耦**。所有 LLM / Embedding 调用统一走模型服务出口，上层不直连大模型，便于切换供应商与做可观测。

## 三、模型选型：本地向量 + 云端大模型

- **大模型**：采用阿里云通义千问 Qwen，通过 DashScope API 调用，凭证走环境变量。
- **向量模型**：采用本地部署的 bge-m3，JVM 进程内 ONNX Runtime 推理，输出 **1024 维**归一化向量，不依赖外部 HTTP 推理服务，启动时加载、常驻内存。

维度一致性是 RAG 成败关键：ES 索引 `writing_material_chunk` 的 embedding 字段 dense_vector 的 dim 必须与模型输出一致（1024），检索距离用余弦相似度。

## 四、素材 RAG：从上传到可检索

一条完整的素材链路：

1. **解析**：POI 解析 docx、PDFBox 解析 pdf、txt/md 直接读取，统一输出纯文本；
2. **切片**：固定长度（默认 512 字）+ 重叠（默认 50 字），保证切片间上下文衔接；
3. **向量化**：每个切片调用 Embedding 模型映射为向量；
4. **入库**：批量写入 ES，携带用户维度与素材关联；
5. **检索**：按用户 + 语义相似度返回 TopN 相似片段，注入仿写提示词。

关键设计：**用户维度贯穿全链路**——切片与检索都强制带 user_id，保证不同用户的数据严格隔离；**失败可回退**——任一步骤失败整体报错，不产生孤儿数据。

## 五、记忆分层：短期、长期、核心

为了让对话"越聊越懂你"，记忆拆成三层：

- **短期记忆**：会话上下文，只保留最近 10 轮用户输入与模型回复，丢弃思考过程与工具中间态，存在 Redis；
- **长期记忆**：跨会话可复用的用户偏好、写作风格、习惯术语，显式回写到 MySQL；
- **核心记忆**：系统角色、写作原则等固定 Prompt，始终注入最前。

压缩顺序有讲究：先抽取长期记忆，再压缩会话，避免把该沉淀的偏好当成噪音丢掉。

## 六、三类写作的编排

| 任务 | 路由 | 关键能力 |
|------|------|----------|
| 一句话写作 | 多轮对话 | 短期记忆 + 流式输出 |
| 素材仿写 | RAG 检索注入 | 参考片段 + 用户需求 + 对话历史组装提示词 |
| 模板写作 | 变量填充 | 动态表单收集变量 → 占位符替换 → 生成 |

三类任务共享同一套底座（Agent、记忆、模型服务、存储），只是入口和提示词组装不同。

## 七、上线要点

- **配置一律环境变量**，无明文密钥；
- **逻辑删除 + 审计**：所有业务表删除走逻辑删除，记录创建审计；
- **流式体验**：SSE 长文增量渲染，避免长时间白屏；
- **回归保障**：每个功能开发期把验收测试固化为自动化测试，防止后面改动破坏前面。

## 八、总结

企业级 AI 写作引擎的难点不在"调通一次生成"，而在**稳定性、隔离性、可维护性**。把架构分层做干净、把用户维度做彻底、把记忆与检索底座打牢，三种写作能力只是底座之上的三个入口。
